# Budget App Design System

Status: Active v0.2
Scope: Mobile-first personal budget tracking application  
Purpose: Source of truth for visual language, interaction patterns, and UI implementation

## 1. Product Experience

The app should make money feel understandable, calm, and manageable. It should avoid the visual anxiety common in financial products: dense dashboards, aggressive red/green signals, excessive charts, and decorative complexity.

The experience should feel:

- Calm: clear hierarchy, generous whitespace, and restrained use of color.
- Trustworthy: accurate formatting, predictable patterns, and professional typography.
- Focused: one primary task or insight per screen.
- Human: plain language, friendly empty states, and supportive feedback.
- Efficient: common actions are reachable with one hand and require minimal input.

### Design principles

1. **Clarity before density**  
   Show the most important amount or decision first. Secondary context can follow.

2. **Whitespace is structure**  
   Use spacing to group content before adding borders, backgrounds, or dividers.

3. **Color communicates meaning**  
   Brand color indicates action and selection. Semantic colors indicate financial status. Avoid decorative color noise.

4. **Progress, not judgment**  
   Use neutral language such as “Above plan” rather than “Bad spending.”

5. **Details on demand**  
   Summaries stay simple. Transactions, category details, and explanations appear through drill-down views.

6. **Thumb-friendly by default**  
   Primary actions and navigation belong in the lower, easily reachable portion of mobile screens.

## 2. Visual Direction

The visual style is airy and minimal with slightly softened geometry. Surfaces should feel crisp and professional rather than playful or pill-heavy.

- Mostly flat surfaces with subtle tonal separation.
- Borders are preferred over shadows.
- Corners are softly rounded, usually 10–14px.
- Full pills are reserved for tags, filters, and status—not cards or primary layout.
- Icons use a consistent 1.75–2px stroke.
- Charts use a small, stable color set and direct labels where possible.
- Motion is subtle and functional.

## 3. Color System

The initial palette combines cool blue for trust and action with warm neutral backgrounds. Colors should be implemented as semantic tokens so the palette can evolve without rewriting components.

| `surface` | `#FFFFFF` | Cards, sheets, inputs |
| `surface-subtle` | `#F0F2EF` | Grouped sections, inactive controls |
| `foreground` | `#17201D` | Primary text |
| `foreground-muted` | `#69736F` | Secondary text |
| `foreground-subtle` | `#929B97` | Tertiary labels, placeholders |
| `border` | `#E1E5E2` | Default border and divider |
| `border-strong` | `#C9CFCC` | Focused or emphasized boundaries |
| `primary` | `#356B68` | Primary actions and selected states |
| `primary-hover` | `#2D5B58` | Hover state |
| `primary-active` | `#244A48` | Pressed state |
| `primary-soft` | `#E2EFED` | Selected backgrounds and highlights |
| `on-primary` | `#FFFFFF` | Text/icons on primary |
| `income` | `#2F7D5A` | Positive cash flow |
| `income-soft` | `#E5F3EB` | Positive status background |

### Dark theme

Dark mode is planned, but the first implementation should prioritize a complete and accessible light theme. Dark values should be designed as a separate palette, not generated by simply inverting light colors.

### Color usage rules

- Never rely on color alone to distinguish income, expense, warning, or error.
- Pair semantic color with a sign, icon, label, or pattern.
- Use `primary` for interaction, not for every heading or decorative surface.
- Use `expense` only when the distinction is useful; regular transaction amounts may use `foreground`.
- Avoid pure black and pure white as large app backgrounds.
- Maintain WCAG AA contrast for text and essential controls.

## 4. Typography

Use Geist Sans as the primary typeface. It is neutral, compact, and well suited to financial data. Use tabular numerals for amounts so changing values remain visually stable.

### Type scale

| Style | Size / line height | Weight | Usage |
|---|---:|---:|---|
| Display | 36 / 40px | 600 | Total balance or major result |
| Title 1 | 28 / 34px | 600 | Screen title |
| Title 2 | 22 / 28px | 600 | Section or detail title |
| Title 3 | 18 / 24px | 600 | Card title |
| Body large | 17 / 26px | 400 | Prominent supporting copy |
| Body | 15 / 22px | 400 | Default UI text |
| Body strong | 15 / 22px | 600 | Labels and emphasized values |
| Caption | 13 / 18px | 400 | Metadata and helper text |
| Caption strong | 13 / 18px | 600 | Compact labels and badges |
| Micro | 11 / 16px | 500 | Chart axes only; avoid elsewhere |

### Typography rules

- Use sentence case for headings, buttons, navigation, and labels.
- Amounts use tabular numerals and no unnecessary trailing decimals.
- Use weight and spacing before increasing font size.
- Limit text to three hierarchy levels on one screen.
- Avoid uppercase labels except short currency codes such as USD.
- Never use color as the only difference between heading levels.

## 5. Money and Data Formatting

Financial formatting must be consistent across all screens.

- Display the user’s selected currency and locale.
- Use `$1,240` in summaries and `$1,240.50` where exact cents matter.
- Use an explicit sign for transaction flows: `+$240.00`, `−$48.20`.
- Use a true minus sign (`−`), not a hyphen.
- Keep the currency symbol attached to the amount.
- Use `Today`, `Yesterday`, then localized dates in transaction lists.
- Percentages use at most one decimal place.
- Zero states use `$0`, not an em dash, when zero is meaningful.
- Negative balances must include a sign and accessible semantic label.
- Never abbreviate important editable values. Compact chart labels may use `$1.2k`.

## 6. Spacing and Layout

Use a 4px base grid with an airy default rhythm.

### Spacing tokens

| Token | Value | Typical use |
|---|---:|---|
| `space-1` | 4px | Tight icon/text adjustment |
| `space-2` | 8px | Related inline content |
| `space-3` | 12px | Compact component padding |
| `space-4` | 16px | Default gap and mobile gutter |
| `space-5` | 20px | Card padding |
| `space-6` | 24px | Section spacing |
| `space-8` | 32px | Major section separation |
| `space-10` | 40px | Screen-level separation |
| `space-12` | 48px | Large composition spacing |

### Layout rules

- Mobile page gutter: 16px below 390px; 20px at 390px and above.
- Maximum content width: 720px for focused app screens.
- Desktop shell maximum width: 1200px where multi-column layouts are useful.
- Default card padding: 20px.
- Default vertical section gap: 32px.
- Use dividers only when spacing cannot communicate the grouping.
- Respect device safe areas at the top and beneath bottom navigation.

### Responsive breakpoints

| Name | Width | Intended behavior |
|---|---:|---|
| Mobile | `< 640px` | Single column, bottom navigation |
| Tablet | `640–1023px` | Wider single column or selective two-column views |
| Desktop | `≥ 1024px` | Persistent side navigation and optional detail column |

Mobile is the primary design target. Larger layouts should enhance the same information architecture rather than introduce different workflows.

### Mobile form behavior

- Creation and editing screens must work without page-level horizontal overflow at 320px, 390px, and 430px widths.
- Use 16px card padding on narrow phones, increasing to 20px from 390px when the extra space improves readability.
- Interactive controls must remain at least 44 × 44px, including color swatches, upload controls, and icon buttons.
- Long preset rows, such as account or category colors, may scroll horizontally. Hide the visual scrollbar, use scroll snapping, and include a short “Swipe to see more” hint.
- Preset images and upload controls wrap onto another line instead of shrinking below their usable size.
- Dense icon grids use three columns below 360px and four columns from 360px upward. Labels may truncate, but their accessible names must remain complete.
- Preview cards must protect long names and large amounts with `min-width: 0`, truncation, and responsive type sizing.
- Mobile date and time pickers use a bottom drawer rather than a full-screen page. The drawer respects top and bottom safe areas, has rounded top corners, a dimmed backdrop, a visible drag handle, and a sticky header with explicit close and Done actions.
- Goal target dates use the same bottom-drawer calendar pattern. The current date is highlighted by default, selecting a date updates the form without dismissing the drawer, and the user confirms with Done; native browser date popovers are not used.
- Mobile choice fields use the same bottom-drawer picker pattern as calendars. Do not use native `<select>` controls in creation or editing forms when a choice can be presented as a branded, thumb-friendly list with an explicit close or Done action.

## 7. Shape, Border, and Elevation

### Radius tokens

| Token | Value | Usage |
|---|---:|---|
| `radius-sm` | 6px | Tags, small controls |
| `radius-md` | 10px | Inputs, buttons, compact cards |
| `radius-lg` | 14px | Main cards, sheets, dialogs |
| `radius-xl` | 18px | Rare hero or onboarding surfaces |
| `radius-full` | 999px | Avatars, status dots, filter chips only |

### Border and shadow

- Default border: 1px solid `border`.
- Strong or focused border: 1px solid `border-strong`.
- Cards should normally use either a border or tonal surface separation.
- Use a shadow only for floating layers such as bottom sheets, menus, and dialogs.
- Recommended floating shadow: `0 12px 32px rgb(23 32 29 / 0.12)`.
- Avoid multiple elevation levels on the same screen.

## 8. Iconography

Use Lucide icons throughout the product.

- Default icon size: 20px.
- Compact icon size: 16px.
- Navigation icon size: 22–24px.
- Default stroke width: 1.75px.
- Icons need text labels for primary navigation and unfamiliar actions.
- Do not mix filled and outline styles except for a clearly selected navigation state.
- Category icons sit on soft tinted backgrounds, not saturated circles.

## 9. Navigation

### Mobile bottom navigation

Bottom navigation is the primary mobile navigation pattern. It remains fixed to the viewport and accounts for the device safe area.

Recommended destinations:

1. **Home** — balance, current budget health, and recent activity
2. **Transactions** — searchable and filterable transaction history
3. **Add** — central primary action for a transaction
4. **Budgets** — category budgets and progress
5. **Profile** — accounts, preferences, and settings

#### Bottom navigation specification

- Height: 64px plus bottom safe area.
- Background: `surface` with a subtle top border.
- Each destination has an icon and a short text label.
- Selected item uses `primary`; unselected items use `foreground-muted`.
- Labels use the Caption Strong style.
- Minimum touch target: 48 × 48px.
- The Add action may use a contained 48px rounded-square button with `radius-lg`.
- Avoid a large floating circular action button; it conflicts with the restrained geometry.
- Navigation should not cover content. Page bottoms include navigation height plus 16px breathing room.
- Hide the bottom navigation during focused flows such as onboarding, authentication, and full-screen transaction entry.

### Desktop navigation

At desktop width, bottom navigation becomes a left navigation rail. Keep the same destinations, labels, and order to preserve spatial familiarity.

## 10. Core Components

### Buttons

Variants:

- Primary: filled `primary`, for the main action on a screen.
- Secondary: `surface` with border, for important alternatives.
- Ghost: transparent, for low-emphasis actions.
- Destructive: use sparingly for irreversible actions.
- Icon: square control with an accessible label.

Rules:

- Default height: 44px; large height: 48px.
- Page-level icon actions use a consistent 44 × 44px square with `radius-md`.
- Neutral actions such as Back, Close, and Cancel use a `surface` background with the default border and `foreground` icon.
- Confirmation actions such as Apply, Done, and Save use `primary-soft`, a `primary` icon, and a subtle `primary` border. A confirmed state may invert to filled `primary`.
- Place cancel/back on the far left and confirmation on the far right of focused-flow headers.
- Route-level headers are sticky. Their bottom divider is transparent while the page is at the top and appears after the user scrolls more than 4px. Keep the full header unit together: navigation action, title, and trailing actions.
- The sticky header owns top and safe-area padding. Do not place route-level top padding on its parent container; that causes the header to shift before sticking and can clip its upper edge.
- Use the Lucide `X` icon for cancel and `Check` for confirmation; both require explicit accessible labels describing the action.
- Horizontal padding: 16–20px.
- Radius: `radius-md`.
- Use one primary button per visible section.
- Button labels use verbs: “Add transaction,” “Save budget,” “Try again.”
- Loading preserves button width and replaces or accompanies the icon.
- Disabled state must remain legible and should explain why when unclear.

### Inputs

- Default height: 48px.
- Radius: `radius-md`.
- Label appears above the field; placeholders do not replace labels.
- Helper or error text appears below without shifting unrelated content.
- Focus uses a 2px `primary` ring with sufficient offset.
- Every add or edit money interaction opens the shared in-app numpad and calculator sheet; do not use a plain text or native number input for money.
- The money editor keeps the formatted amount and currency visible while entering values.
- Keep the original applied amount visible beneath the live draft throughout the editing session so users can compare the old and new values before choosing Set.
- Place digits and decimal entry in the main keypad. Keep `÷`, `×`, `−`, `+`, and `=` in a visually separate calculator rail.
- Opening the editor copies the current value into a draft. Cancel discards the draft; Set applies it to the underlying form.
- Support backspace, a single decimal separator, chained calculations, and results rounded to the currency’s supported precision.
- The sheet anchors to the bottom, respects the bottom safe area, and uses a dimmed backdrop that may be tapped to cancel.
- Amount validation runs against the applied value after Set and remains specific to the field’s rules, such as transactions being greater than zero.
- Group related date, account, and category choices into clear rows.

### Horizontal account selectors

Account choices in transaction, goal, and transfer flows use the shared mobile
horizontal selector pattern. Keep the row in normal document flow and let it
scroll horizontally rather than stacking every account into a tall list.

- Use a labeled `fieldset`/`legend` and include the selected account currency in
  the label when it clarifies the amount context.
- Render each account as a compact, shrink-resistant card with the account
  avatar, short name, and current balance.
- Keep cards at least 56px tall and 44px wide-touch-safe; use `shrink-0`,
  `overflow-x-auto`, hidden scrollbars, and `overscroll-x-contain` so swiping
  does not create page-level horizontal overflow.
- Use the account's assigned pale background and foreground colors. The
  selected card uses that background plus the existing check affordance;
  unselected cards remain neutral but keep their account-colored border.
- Preserve keyboard and assistive technology state with `aria-pressed` on each
  option. Do not replace this pattern with a native select or a vertical stack
  unless there are too few choices for scrolling to be meaningful.

### In-app choice controls

- User-facing choices such as accounts, categories, types, frequencies, and currencies use the app's styled button or bottom-drawer picker pattern.
- Never use an unstyled native browser `<select>` for a product choice; it is visually inconsistent and difficult to use reliably on mobile.
- The trigger keeps the selected value visible, shows the relevant supporting detail such as currency, and exposes its expanded state with `aria-expanded`.
- Picker drawers use a dimmed backdrop, drag handle, clear title, explicit close action, tappable option rows, and an accessible selected state.

### Cards

Cards organize a coherent concept, not every piece of content.

- Default padding: 20px.
- Radius: `radius-lg`.
- Prefer a 1px border and no shadow.
- A card may have one primary value, one supporting label, and one clear action.
- Nested cards are discouraged; use grouped rows instead.

Key card types:

- Account cards use one assigned light-theme background preset per account. Presets should be pale enough to preserve dark foreground text and must not compete with green/red financial semantics.
- Every account has a distinct custom image or avatar. Keep it in a compact rounded-square frame and use the same image consistently anywhere that account appears.

- Balance summary
- Budget progress
- Spending insight
- Account summary
- Empty-state prompt

### Transaction row

- Minimum height: 64px.
- Left: category icon or merchant mark.
- Center: merchant/category and date/account metadata.
- Right: signed amount and optional status.
- Rows use whitespace first; subtle dividers begin after the leading icon.
- Pending transactions include a text label, not reduced opacity alone.

### Budget progress

- Show category name, spent amount, limit, and remaining amount.
- Progress bar height: 8px with rounded ends.
- Normal progress uses `primary`.
- Near limit uses `warning` at 80% or above.
- Over limit uses `expense` and a clear “Over by …” label.
- Do not use red for ordinary spending below the limit.

### Chips and filters

- Height: 32–36px.
- Radius: `radius-full` is allowed.
- Unselected: `surface` with border.
- Selected: `primary-soft` with `primary` text.
- Keep labels short and avoid using chips as primary actions.

### Bottom sheets

Use bottom sheets for focused mobile choices such as category, account, date, and filters.

- Top corners: `radius-xl`.
- Maximum initial height: approximately 85% of viewport.
- Include a visible title and close action.
- Drag handle is supplementary and never the only close mechanism.
- Primary action remains reachable above the safe area.

### Calendar and transaction time picker

The transaction date/time control uses the mobile bottom-drawer pattern shown in the transaction editor:

- Open from the compact transaction date row; do not open a native browser date popover.
- Place the calendar near the top of the drawer for thumb-friendly month navigation and date selection.
- Keep the time control directly below the calendar in its own surface, with a clear “Transaction time” label and the helper text “When it happened in real life.”
- Offer a few useful quick-time presets, while retaining a standard time input for an exact custom time.
- Selecting a calendar date updates the draft but does not close the drawer; the user can choose both date and time before tapping Done.
- Always highlight the current calendar date with a distinct, accessible treatment (for example, a subtle `primary-soft` fill and `primary` outline or ring). The selected transaction date may use a stronger selected style, but the current-date treatment must remain distinguishable when the two are different.
- Use `transaction_at` for the real-world transaction timestamp. Keep `date` as the calendar-day index used for grouping and filtering; never substitute `createdAt` or `updatedAt` for the transaction’s actual time.

### Feedback

- Toasts confirm lightweight actions and disappear automatically.
- Inline messages explain errors near the source.
- Dialogs are reserved for destructive or consequential decisions.
- Success feedback should be brief and should not block the next task.
- Skeletons mimic final structure; avoid generic spinners for initial page loading.

### Offline and notification behavior

- User settings are usable offline. The most recent notification settings are cached locally and changes are applied optimistically.
- Settings synchronize with the backend when connectivity returns. Offline confirmation must say that the change was saved on this device when a server sync is not available.
- Native notifications use the browser Notification API and the service worker so the same interaction works in a browser and in an installed PWA on mobile.
- Request notification permission only after an explicit user action such as “Enable alerts.” Never request permission on page load.
- If permission is denied, keep a visible “How to allow” action and explain that the user must change this site’s permission in browser or device settings. Do not repeatedly trigger a blocked permission prompt.
- Always provide a “Test notification” action. Disable it until permission is granted and explain why it is unavailable.
- Push subscription data is optional. Local notification preferences must continue to work without a VAPID key or a network connection.

## 11. Core Screen Patterns

### Home

Order content by decision value:

1. Greeting and profile access
2. Available balance or safe-to-spend amount
3. Current month budget progress
4. One useful spending insight
5. Recent transactions

Avoid placing more than one chart above the fold.

### Transactions

- Sticky screen header with search and filter access.
- Transactions grouped by date.
- Persistent Add access remains in bottom navigation.
- Filters open in a bottom sheet on mobile.
- Empty search results preserve the query and offer a clear reset action.

### Add transaction

- Amount is the first and most visually prominent input.
- Expense/income selection appears near the amount.
- Category, account, date, note, and recurring options follow.
- Save action is anchored near the bottom but remains visible above the keyboard.
- Advanced fields are collapsed until requested.

### Budgets

- Start with the month summary and remaining amount.
- List categories by urgency or user-defined order.
- Make “spent,” “remaining,” and “limit” visually distinct and consistently positioned.
- Editing a budget opens a focused sheet or detail screen.

### Profile and settings

- Group settings into Account, Preferences, Data, and Security.
- Keep Personal information, Currency and region, Notifications, and Security as separate bordered sections with consistent 14px card corners.
- Email is read-only in the profile screen. Name, currency, and avatar use focused edit controls with immediate saved feedback.
- Notification settings include separate controls for goal milestones, recurring payment due alerts, recurring transaction entry reminders, and low-balance alerts.
- Recurring transaction entry reminders reveal local time and frequency only when enabled. Use a time input and a custom in-app frequency picker with Daily, Weekly, and Monthly options; do not rely on an unstyled browser-native dropdown.
- The recurring reminder time is displayed and stored in the user’s local time. Frequency changes save independently and remain available offline.
- Destructive actions appear at the end, separated from routine settings.
- Currency, locale, and start-of-week settings explain their downstream effect.

### Product voice and copy

- Use concise, factual labels and descriptions that explain the current state or available action.
- Avoid aspirational, motivational, anthropomorphic, or AI-sounding sentences such as “Keep the important things moving.”
- Do not add marketing-style copy to operational screens; prefer direct language such as “Recurring transactions,” “Upcoming,” and “Review before posting.”
- Operational overview content should sit on the page background with the screen header and navigation; avoid nested colored dashboard cards when a seamless section will work.

## 12. Motion

Use Framer Motion for purposeful transitions only.

### Motion tokens

| Token | Duration | Usage |
|---|---:|---|
| `motion-fast` | 120ms | Press, hover, selection |
| `motion-base` | 180ms | Component state changes |
| `motion-slow` | 260ms | Sheet and page-level transitions |

Recommended easing:

- Enter: `[0.22, 1, 0.36, 1]`
- Exit: `[0.4, 0, 1, 1]`

Rules:

- Animate opacity and transform where possible.
- Avoid bouncing financial amounts or status changes.
- Amount transitions should preserve readability.
- Bottom sheets move vertically; menus use subtle opacity and scale.
- Respect `prefers-reduced-motion` and provide an effectively static experience.

## 13. Accessibility

- Target WCAG 2.2 AA.
- Minimum touch target: 44 × 44px; use 48px for primary mobile navigation.
- Body text should not be smaller than 15px.
- Focus indicators must remain visible and consistent.
- All icon-only buttons require accessible names.
- Inputs require persistent labels and programmatically associated errors.
- Custom menus expose their expanded state, selected option, and keyboard focus to assistive technology.
- Charts require a text summary and accessible data representation.
- Do not communicate budget status by color alone.
- Support text zoom to 200% without loss of content or action.
- Support keyboard navigation for all desktop and tablet interactions.
- Announce saved transactions and validation failures to assistive technology.
- Permission-denied notification states must include a plain-language recovery action and must not rely on color alone.

## 14. Content Voice

The voice is concise, calm, and factual.

Prefer:

- “You have $420 left this month.”
- “Dining is close to its limit.”
- “No transactions yet.”
- “We couldn’t save this transaction. Try again.”

Avoid:

- “Great job!” for routine financial activity.
- “You overspent badly.”
- “Oops!” for errors involving money.
- Ambiguous actions such as “Continue” when “Save transaction” is clearer.

## 15. Initial Component Inventory

The first implementation phase should establish:

1. Design tokens and global theme
2. App shell and responsive navigation
3. Button, icon button, input, select, and textarea
4. Card and section header
5. Amount display
6. Transaction row and transaction group
7. Budget progress
8. Chip and filter controls
9. Bottom sheet and dialog
10. Notification settings and permission states
11. Custom select / menu control
12. Empty, loading, error, and toast states

Components should be built as small variants over the shadcn foundation. Avoid creating a separate abstraction until a pattern appears at least twice.

## 16. Definition of Done

A screen is design-complete when:

- It has a clear primary purpose and one dominant action.
- Mobile behavior is designed at 320px, 390px, and 430px widths.
- Tablet and desktop adaptation is defined where relevant.
- Loading, empty, error, and success states are covered.
- Content works with long labels and large monetary values.
- Keyboard, focus, contrast, touch targets, and reduced motion are verified.
- Bottom navigation and safe-area spacing do not obscure content.
- Formatting follows the money and data rules in this document.

## 17. Open Decisions

These choices should be resolved before polishing the first full screen:

1. **Primary dashboard metric**  
   Choose between total balance, safe-to-spend, or remaining monthly budget.

2. **Transaction model**  
   Confirm whether the app supports cash accounts, bank syncing, manual entry, or a combination.

3. **Budgeting method**  
   Confirm category limits, envelope budgeting, zero-based budgeting, or a simpler monthly plan.

4. **Brand personality**  
   Decide whether the visual identity should lean more warm and lifestyle-oriented or more neutral and finance-oriented.

5. **Theme scope**  
   Decide whether dark mode is required for the first release or follows after the light theme.

6. **Navigation labels**  
   Validate “Home,” “Transactions,” “Add,” “Budgets,” and “Profile” against the final feature set.

## 18. Proposed Next Step

Create a low-fidelity mobile structure for the Home screen and Add Transaction flow using this system. Validate hierarchy, navigation, and financial terminology before adding visual polish or implementing components.
